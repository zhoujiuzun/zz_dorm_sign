# 2. 存储用 OSS 上的 JSON 文件（名册与历史分离），而非数据库

日期: 2026-06-17

## 状态

已接受

## 背景

注册接口需写入新用户的 OpenID，每日定时器需读出全部用户、并把每次签到结果追加到历史。
两者都跑在阿里云函数计算（FC）上——FC 无持久磁盘、函数结束即清空内存，因此原 `--fc`
模式从环境变量读用户的方式无法支持"运行时新增用户"。需要一个两个函数都能读写的外部存储。

受众为"自己 + 少数熟人"，用户数量在个位到几十之间，写入极低频（一人一辈子注册一次），
读取每天 4 次。

候选：OSS 上单个 JSON 文件 / 轻量托管数据库（表格存储等）/ 放弃 FC 改用 VPS+本地文件。

## 决策

采用 **OSS 上的 JSON 文件**，并拆为两个：

- `users.json` —— 名册，每人 `{openid, 昵称}`。注册接口写入，定时器读取。几乎不增长。
- `history.json` —— 签到流水，每次签到追加一条 `{昵称, 日期, 时间, 结果}`。定时器写入，
  状态页读取。每天每人一条，**永久保留**。

## 理由

- 数据量极小、并发几乎为零，关系型/表格存储的能力全部用不上，是过度设计。
- 复用 `sign.py` 已有的 `load_config`/`save_config` JSON 读写逻辑，改动最小。
- OSS 在 FC 免费额度内成本几乎为零，且不必维护常驻服务器（排除 VPS 方案，
  与 [ADR-0001](0001-openid-capture-local-pc.md) "永久在线部分尽量 Serverless" 一致）。
- **名册与历史分离**：名册含明文 OpenID（敏感、几乎不变），历史是天天追加的流水
  （不含 OpenID）。拆开后状态页只读 `history.json`，物理上接触不到 OpenID，更安全；
  也避免每天重写那个含敏感数据的文件。
- 历史永久保留：5 人 × 365 天 ≈ 不到 200KB/年，存储成本可忽略，无需淘汰旧记录。

## 后果

- 并发写有极小概率互相覆盖（两人同一秒注册，或注册与定时器同时写）。在本规模下可接受；
  如需更稳可加 OSS 条件写/版本号，但初版不做。
- `users.json` 含明文 OpenID（敏感），OSS 桶 `zhouhuanzhang`（cn-beijing，私有）必须保持
  禁止公开读，仅 FC 函数凭 RAM 角色访问。
- 状态页只读取 `history.json`，只展示昵称与签到结果，物理上不接触 OpenID。
- FC 与 OSS 同处 cn-beijing，函数读写走内网 endpoint（`oss-cn-beijing-internal.aliyuncs.com`），
  免流量费且更快。
